# Сборка, настройка и тестирование CryptoPro Bridge

> **Статус документа:** инструкция для разработчика и тестировщика
> Windows.\
> **Назначение:** собрать Windows-компонент
> `MedialogSign.CryptoProBridge.exe`, проверить его взаимодействие с
> КриптоПро CSP/CAdESCOM и подключить к Flutter-приложению Medialog
> Sign.

## 1. Что входит в модуль

Модуль состоит из двух частей:

1.  **Windows Bridge** --- консольное приложение на C#, которое
    обращается к COM-компоненту CAdESCOM и выполняет криптографические
    операции.
2.  **Flutter-клиент** --- Dart-класс `CryptoProBridgeClient`, который
    запускает Windows Bridge как отдельный процесс, передаёт ему JSON
    через `stdin` и получает JSON через `stdout`.

Общая схема:

``` text
Flutter UI
   |
   v
CryptoProBridgeClient (Dart)
   |
   | JSON через stdin / stdout
   v
MedialogSign.CryptoProBridge.exe
   |
   | COM Automation
   v
CAdESCOM
   |
   v
КриптоПро CSP + сертификат + закрытый ключ
```

Bridge не экспортирует закрытый ключ и не принимает PIN-код в JSON. Ввод
PIN-кода, если он требуется носителем или криптопровайдером, выполняется
средствами установленного криптографического ПО.

### Поддерживаемые операции

  -----------------------------------------------------------------------
  Операция                            Назначение
  ----------------------------------- -----------------------------------
  `status`                            Проверка доступности COM-классов
                                      CAdESCOM

  `list-certificates`                 Получение сертификатов из хранилища
                                      текущего пользователя Windows

  `sign-detached`                     Создание отсоединённой CAdES-BES
                                      подписи

  `sign-attached`                     Создание присоединённой CAdES-BES
                                      подписи

  `verify-detached`                   Проверка отсоединённой подписи
  -----------------------------------------------------------------------

Текущая реализация не является полноценным менеджером сертификатов и не
выполняет все проверки доверия, необходимые для промышленного
документооборота. Подробности приведены в разделе [12. Ограничения
реализации](#12-ограничения-текущей-реализации).

## 2. Требования к рабочей станции

Для сборки и проверки потребуется Windows-машина. Сборка и работа
COM-моста не предназначены для Linux или macOS.

### 2.1. Операционная система

-   Windows 10 или Windows 11;
-   архитектура x64;
-   учётная запись Windows, в профиле которой доступны тестовые
    сертификаты;
-   права на чтение тестовых файлов и запись результатов подписи.

### 2.2. Средства разработки

Установите один из вариантов:

-   Visual Studio 2022;
-   Visual Studio 2022 Build Tools с компонентами разработки
    классических приложений .NET.

Также необходим **.NET Framework 4.8 Developer Pack**. Наличие только
.NET Runtime не гарантирует, что проект удастся собрать.

В Visual Studio Installer проверьте наличие компонентов, связанных с
разработкой приложений .NET Desktop и сборкой проектов .NET Framework.

### 2.3. Криптографическое ПО

На машине должны быть установлены и настроены:

-   КриптоПро CSP подходящей версии;
-   совместимый компонент CAdESCOM;
-   COM-регистрация CAdESCOM, доступная приложению x64;
-   тестовый сертификат в хранилище `CurrentUser\My`;
-   доступ к закрытому ключу тестового сертификата.

Версии CSP, CAdESCOM, разрядность и способ установки зависят от
инфраструктуры организации. Сверяйте их с документацией и требованиями
установленной версии КриптоПро.

> Важно: наличие КриптоПро CSP само по себе не доказывает, что CAdESCOM
> установлен и зарегистрирован. Это отдельная проверка.

### 2.5. Особенности Windows Server

Перед развёртыванием определите, как именно будет работать приложение.

**Сценарий A. Flutter-приложение запускается в интерактивной сессии Windows Server**

Например, оператор подключается к серверу по Remote Desktop (RDP), входит под отдельной доменной или локальной учётной записью и запускает Medialog Sign как обычное Windows-приложение.

В этом сценарии:
- Flutter UI работает в пользовательской сессии;
- Bridge запускается дочерним процессом от имени того же пользователя;
- `CurrentUser\\My` означает хранилище сертификатов вошедшего пользователя;
- диалоги PIN-кода или подтверждения операции могут отображаться в этой сессии, если это поддерживается CSP, носителем и политиками сервера;
- при отключении RDP-сеанса поведение криптопровайдера и носителя необходимо проверить отдельно.

Для такого развёртывания настройте отдельную учётную запись Windows для приложения или оператора, ограничьте интерактивный вход, права на каталоги и доступ к сертификатам. Не запускайте приложение от имени Domain Admin или Local System без отдельного обоснования.

**Сценарий B. Подписание должно выполняться в фоне, без входа пользователя**

Текущий модуль не является Windows-службой и не должен просто запускаться из службы Windows в Session 0. В таком режиме могут быть недоступны интерактивные диалоги, пользовательское хранилище сертификатов, PIN-подтверждение и устройства, требующие активной сессии.

Для фонового серверного подписания потребуется отдельная серверная архитектура:
- выделенный Windows Service или worker-процесс с контролируемой учётной записью;
- заранее определённая модель хранения и доступа к сертификату и закрытому ключу;
- поддержка неинтерактивной аутентификации со стороны конкретного CSP/носителя;
- очередь заданий, контроль повторов, тайм-ауты и аудит;
- разграничение прав на исходные документы и подписи;
- отдельные тесты отказоустойчивости и безопасности.

Не переносите PIN-коды в конфигурационные файлы, переменные окружения, аргументы командной строки или JSON. Если используемый носитель требует интерактивного ввода PIN, полностью фоновое подписание может быть невозможно без смены модели ключевого хранилища или оборудования.

**Не смешивайте эти два сценария.** Успешный тест в RDP-сеансе не доказывает, что подпись будет работать после выхода пользователя из системы или при запуске службы.

### 2.4. Проверка Flutter

Для интеграционного теста Flutter-приложения дополнительно установите:

-   Flutter SDK;
-   Dart SDK, поставляемый с Flutter;
-   Visual Studio с компонентами для сборки Windows-приложений Flutter;
-   зависимости самого Flutter-проекта.

Проверка:

``` powershell

```

Если Flutter-проект ещё не создан или не настроен для Windows, сначала
выполните его настройку. Этот документ описывает подключение Bridge к
готовому Flutter Windows-приложению.

## 4. Сборка Windows Bridge

### 4.1. Сборка через Visual Studio

1.  Откройте `windows_bridge\MedialogSign.CryptoProBridge.csproj` в
    Visual Studio.
2.  В конфигурации решения выберите `Release`.
3.  В платформе выберите `x64`.
4.  Выполните **Build → Rebuild Solution**.
5.  Убедитесь, что сборка завершилась без ошибок.

Ожидаемый путь к EXE:

``` text
windows_bridge\bin\Release\MedialogSign.CryptoProBridge.exe
```

Если Visual Studio выводит EXE в другой каталог, используйте фактический
путь. Не переименовывайте файл без необходимости: Flutter-клиент должен
запускать именно тот EXE, который вы собрали.

### 4.2. Сборка из Developer PowerShell

Откройте Developer PowerShell for Visual Studio. Перейдите в корень
репозитория и выполните:

``` powershell
msbuild .\windows_bridge\MedialogSign.CryptoProBridge.csproj /t:Rebuild /p:Configuration=Release /p:Platform=x64
```

Проверьте наличие результата:

``` powershell
Test-Path .\windows_bridge\bin\Release\MedialogSign.CryptoProBridge.exe
```

Ожидаемый результат:

``` text
True
```

Если `msbuild` не найден, используйте Developer PowerShell либо откройте
проект в Visual Studio.

### 4.3. Что делать при ошибке сборки

Если сборка сообщает, что не найден reference assembly .NET Framework
4.8:

-   установите .NET Framework 4.8 Developer Pack;
-   перезапустите Visual Studio;
-   выполните Rebuild.

Если платформа `x64` отсутствует:

-   откройте Configuration Manager;
-   создайте или выберите платформу `x64`;
-   проверьте, что проект собирается именно для x64.

Если ошибка связана с COM:

-   проверьте, что проблема действительно возникает на этапе сборки, а
    не при запуске;
-   COM-компонент CAdESCOM обычно требуется на целевой машине во время
    выполнения;
-   проверьте ссылки и настройки проекта, не подменяя их случайными DLL
    из другого комплекта SDK.

Не копируйте произвольные COM-библиотеки из SDK в каталог приложения.
Установка и регистрация компонентов должны выполняться поддерживаемым
установщиком КриптоПро.

## 5. Протокол обмена с Bridge

Bridge запускается как отдельный процесс. За один запуск он получает
один JSON-объект из стандартного ввода (`stdin`) и возвращает один
JSON-ответ в стандартный вывод (`stdout`).

Пример запроса:

``` json
{"action":"status"}
```

Успешный ответ имеет общую оболочку:

``` json
{
  "ok": true,
  "action": "status",
  "data": {
    "..."
  }
}
```

Ответ с ошибкой имеет общую оболочку:

``` json
{
  "ok": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Описание ошибки",
    "details": "Дополнительные сведения"
  }
}
```

Фактические поля `data` зависят от операции. При разборе ответа
ориентируйтесь на код текущей версии `Program.cs`, а не на приведённые
сокращённые примеры.

### Правила протокола

-   Кодировка JSON --- UTF-8.
-   В `stdin` передаётся один JSON-объект.
-   В `stdout` ожидается JSON-ответ.
-   Диагностические сообщения не должны подменять JSON-ответ в `stdout`.
-   Пути к файлам должны быть доступны учётной записи, от имени которой
    запущен Bridge.
-   Не передавайте PIN-коды, пароли и закрытые ключи в JSON.
-   Не передавайте в запросах данные реальных документов при первичной
    настройке.

## 6. Проверка Bridge без Flutter

Сначала проверьте C#-компонент отдельно. Это позволяет отделить ошибки
КриптоПро и COM от ошибок Flutter.

Откройте PowerShell в корне репозитория:

``` powershell
$Bridge = (Resolve-Path ".\windows_bridge\bin\Release\MedialogSign.CryptoProBridge.exe").Path
```

### 6.1. Проверка доступности CAdESCOM

Выполните:

``` powershell
'{"action":"status"}' | & $Bridge
```

Проверьте:

-   процесс завершается;
-   возвращается корректный JSON;
-   поле `ok` равно `true`;
-   в `data` присутствуют сведения о доступности COM-классов, которые
    проверяет реализация.

Если `ok` равно `false`, сохраните `code`, `message` и `details`. Не
переходите к тесту подписи, пока не устранена проблема доступности
компонента.

### 6.2. Получение сертификатов

Выполните:

``` powershell
'{"action":"list-certificates"}' | & $Bridge
```

Операция читает сертификаты из хранилища личных сертификатов текущего
пользователя Windows (`CurrentUser\My`).

В ответе для сертификатов предусмотрены поля:

  -----------------------------------------------------------------------
  Поле                                Значение
  ----------------------------------- -----------------------------------
  `thumbprint`                        Отпечаток сертификата

  `subjectName`                       Владелец сертификата

  `issuerName`                        Издатель сертификата

  `serialNumber`                      Серийный номер

  `validFrom`                         Начало срока действия

  `validTo`                           Окончание срока действия

  `hasPrivateKey`                     Признак доступности связанного
                                      закрытого ключа

  `dateRangeValid`                    Признак нахождения текущей даты в
                                      сроке действия

  `isReadyForSigning`                 Сводный признак готовности по
                                      проверкам текущей реализации
  -----------------------------------------------------------------------

Для первого теста выберите сертификат, у которого:

-   `hasPrivateKey` равно `true`;
-   `dateRangeValid` равно `true`;
-   `isReadyForSigning` равно `true`.

`isReadyForSigning` не является полной проверкой доверия к сертификату.
Этот флаг не заменяет проверку цепочки, отзыва и требований принимающей
системы.

Если список пуст, проверьте, что сертификат установлен именно в профиль
того пользователя Windows, от имени которого запускается PowerShell и
Flutter-приложение.

### 6.3. Подготовка тестового файла

Создайте отдельный каталог:

``` powershell
New-Item -ItemType Directory -Force -Path "C:\CryptoProTest"
```

Создайте небольшой текстовый файл:

``` powershell
Set-Content -Path "C:\CryptoProTest\source.txt" -Value "Тест подписи Medialog Sign" -Encoding UTF8
```

Проверьте содержимое:

``` powershell
Get-Content "C:\CryptoProTest\source.txt"
```

Для первичной проверки используйте только искусственные тестовые данные.

### 6.4. Создание отсоединённой подписи

Скопируйте `thumbprint` тестового сертификата из результата
`list-certificates`. Подставьте его вместо значения
`ВСТАВЬТЕ_ОТПЕЧАТОК`.

``` powershell
$Thumbprint = "ВСТАВЬТЕ_ОТПЕЧАТОК"
$Request = @{
    action = "sign-detached"
    inputPath = "C:\CryptoProTest\source.txt"
    outputPath = "C:\CryptoProTest\source.sig"
    thumbprint = $Thumbprint
} | ConvertTo-Json -Compress

$Request | & $Bridge
```

При успешном выполнении должен появиться файл:

``` text
C:\CryptoProTest\source.sig
```

Проверьте его наличие:

``` powershell
Test-Path "C:\CryptoProTest\source.sig"
```

Ожидаемый результат:

``` text
True
```

В текущей реализации результат CAdESCOM записывается в файл как UTF-8
текст. Не меняйте расширение или способ кодирования результата, пока не
согласован формат с системой-получателем.

### 6.5. Проверка отсоединённой подписи

Выполните:

``` powershell
$Request = @{
    action = "verify-detached"
    inputPath = "C:\CryptoProTest\source.txt"
    signaturePath = "C:\CryptoProTest\source.sig"
} | ConvertTo-Json -Compress

$Request | & $Bridge
```

При успешной криптографической проверке ожидается `ok: true` и
`data.valid: true`.

Это подтверждает проверку подписи относительно переданного исходного
файла в рамках текущего вызова CAdESCOM. Это **не означает**, что
сертификат доверенный для любой информационной системы или что проверены
все статусы отзыва и политика организации.

### 6.6. Проверка реакции на изменение исходного файла

Измените исходный файл:

``` powershell
Add-Content -Path "C:\CryptoProTest\source.txt" -Value "Изменение после подписания" -Encoding UTF8
```

Повторите `verify-detached`.

Ожидается, что проверка завершится ошибкой или невалидным результатом.
Подпись не должна считаться корректной для изменённого содержимого.

Если изменённый файл всё ещё проходит проверку, остановите тестирование
и разберите фактический формат подписи и параметры `VerifyCades`. Не
используйте такой результат в рабочем документообороте до выяснения
причины.

## 7. Проверка присоединённой подписи

Для создания присоединённой подписи используйте действие
`sign-attached`:

``` powershell
$Thumbprint = "ВСТАВЬТЕ_ОТПЕЧАТОК"

$Request = @{
    action = "sign-attached"
    inputPath = "C:\CryptoProTest\source.txt"
    outputPath = "C:\CryptoProTest\source-attached.p7s"
    thumbprint = $Thumbprint
} | ConvertTo-Json -Compress

$Request | & $Bridge
```

Проверьте наличие результата:

``` powershell
Test-Path "C:\CryptoProTest\source-attached.p7s"
```

В текущем Bridge предусмотрено создание attached-подписи, но отдельная
операция `verify-attached` пока не реализована. Поэтому создание файла
ещё не подтверждает совместимость результата с принимающей системой.

До промышленного использования необходимо:

1.  определить требуемый формат attached-подписи;
2.  проверить результат независимым средством проверки;
3.  согласовать формат и параметры с системой-получателем;
4.  добавить автоматизированный тест проверки attached-подписи.

в Flutter-проект Medialog Sign по пути:

``` text
lib/integrations/cryptopro/cryptopro_bridge_client.dart
```

``` dart

```

Этот клиент использует `dart:io` и предназначен для Windows Desktop. Не
подключайте его напрямую к Web-сборке или мобильным платформам.

### 8.2. Размещение EXE рядом с приложением

Правила размещения одинаковы для Windows 10/11 и Windows Server. Однако на сервере каталог приложения должен быть доступен только тем учётным записям, которым разрешён запуск и обновление приложения. Не размещайте исполняемые файлы в каталоге, доступном на запись обычным пользователям.

Для Release-сборки рекомендуется такая структура:

``` text
Release/
├── medialog_sign.exe
├── flutter_windows.dll
├── data/
└── cryptopro/
    └── MedialogSign.CryptoProBridge.exe
```

То есть Bridge располагается в подпапке `cryptopro` рядом с основным EXE
приложения.

Соберите Flutter-приложение:


### 8.3. Создание клиента

Пример диагностического вызова:

``` dart
import 'dart:io';

import 'integrations/cryptopro/cryptopro_bridge_client.dart';

Future<void> checkCryptoProBridge() async {
  final appDirectory = File(Platform.resolvedExecutable).parent.path;

  final client = CryptoProBridgeClient(
    executablePath:
        '$appDirectory\\cryptopro\\MedialogSign.CryptoProBridge.exe',
  );

  try {
    final status = await client.status();
    print('CryptoPro status: $status');

    final certificates = await client.listCertificates();

    print('Найдено сертификатов: ${certificates.length}');

    for (final certificate in certificates) {
      print(
        '${certificate.subjectName}: '
        'готов к подписанию = ${certificate.isReadyForSigning}',
      );
    }
  } on CryptoProBridgeException catch (error) {
    print('Ошибка CryptoPro: ${error.code}: ${error.message}');
  }
}
```

В production-интерфейсе не выводите в пользовательский интерфейс
технические детали COM и не записывайте в обычные логи лишние
персональные сведения сертификатов. Для диагностики используйте
контролируемый журнал с ограниченным доступом.

### 8.4. Вызов отсоединённой подписи из Dart

``` dart
final result = await client.signDetached(
  inputPath: r'C:\CryptoProTest\source.txt',
  outputPath: r'C:\CryptoProTest\source.sig',
  certificateThumbprint: certificate.thumbprint,
);
```

`certificate` в примере --- выбранный объект `CryptoProCertificate`,
полученный через `listCertificates()`.

Проверка:

``` dart
final verification = await client.verifyDetached(
  inputPath: r'C:\CryptoProTest\source.txt',
  signaturePath: r'C:\CryptoProTest\source.sig',
);

final isValid = verification['valid'] == true;
```

Для присоединённой подписи:

``` dart
final result = await client.signAttached(
  inputPath: r'C:\CryptoProTest\source.txt',
  outputPath: r'C:\CryptoProTest\source-attached.p7s',
  certificateThumbprint: certificate.thumbprint,
);
```

### 8.5. Обработка ошибок в приложении

Dart-клиент может выбрасывать `CryptoProBridgeException`. Основные коды,
которые следует учитывать на уровне UI:

  -----------------------------------------------------------------------
  Код                                 Значение / действие
  ----------------------------------- -----------------------------------
  `BRIDGE_NOT_FOUND`                  EXE не найден. Проверить путь и
                                      упаковку

  `BRIDGE_START_FAILED`               Не удалось запустить процесс.
                                      Проверить права, файл и системные
                                      зависимости

  `INVALID_BRIDGE_RESPONSE`           Bridge вернул невалидный JSON или
                                      посторонний вывод

  Другие коды Bridge                  Показать безопасное сообщение и
                                      сохранить технические сведения для
                                      диагностики
  -----------------------------------------------------------------------

Не показывайте пользователю необработанный stack trace. Сохраняйте
`code`, `message` и необходимые `details` в защищённый технический
журнал. Не записывайте PIN-код или секреты.

## 10. Диагностика типичных проблем

### 10.1. `BRIDGE_NOT_FOUND`

Причина: Dart-клиент не обнаружил EXE по указанному пути.

Проверьте:

``` dart
print(Platform.resolvedExecutable);
print(File(executablePath).existsSync());
```

Убедитесь, что EXE действительно скопирован в:

``` text
<каталог приложения>\cryptopro\MedialogSign.CryptoProBridge.exe
```

Проверьте регистр и написание имени файла, а также фактический каталог
Flutter Release-сборки.

### 10.2. Bridge запускается, но `status` сообщает об отсутствии CAdESCOM

Возможные причины:

-   CAdESCOM не установлен;
-   компонент установлен, но COM-класс не зарегистрирован;
-   зарегистрирована только несовместимая разрядность;
-   установка КриптоПро или CAdESCOM повреждена;
-   приложение запущено в окружении, где COM-компонент недоступен.

Проверьте установку и регистрацию штатными средствами КриптоПро. Не
исправляйте проблему случайной ручной регистрацией DLL из неизвестного
источника.

### 10.3. Сертификаты не найдены

Проверьте:

1.  Вошли ли вы под тем пользователем Windows, которому принадлежит
    сертификат.
2.  Находится ли сертификат в `CurrentUser\My`.
3.  Не установлен ли он только в `LocalMachine`.
4.  Видит ли сертификат штатное средство просмотра сертификатов Windows
    или КриптоПро.
5.  Подключён ли нужный токен/носитель.

Список сертификатов в текущей реализации ограничен хранилищем
`CurrentUser\My`.

### 10.4. Сертификат найден, но подписать не удаётся

Проверьте:

-   доступность закрытого ключа;
-   подключение токена или другого носителя;
-   корректность PIN-кода, если он требуется;
-   срок действия сертификата;
-   доступность контейнера ключа;
-   права текущего пользователя;
-   поддержку алгоритмов и параметров установленной версией
    CSP/CAdESCOM.

Не пытайтесь обходить PIN-диалог или сохранять PIN в конфигурации
приложения.

### 10.5. `INVALID_BRIDGE_RESPONSE`

Bridge должен возвращать JSON в `stdout`. Если сторонняя библиотека или
диагностический вывод пишет туда обычный текст, Dart-клиент не сможет
разобрать ответ.

Проверьте отдельно:

``` powershell
'{"action":"status"}' | & $Bridge
```

Убедитесь, что в стандартном выводе находится один JSON-объект.
Технические сообщения должны направляться в `stderr`, а не смешиваться с
JSON.

### 10.6. Тайм-аут операции

В Dart-клиенте по умолчанию установлен тайм-аут 90 секунд.

Причинами задержки могут быть:

-   ожидание PIN-кода;
-   диалог выбора носителя или подтверждения операции;
-   медленный или недоступный носитель;
-   большой файл;
-   зависание криптопровайдера или COM-компонента.

Не увеличивайте тайм-аут автоматически, пока не выяснено, на каком этапе
возникает задержка. При отмене пользователем PIN-диалога приложение
должно получить контролируемую ошибку, а не зависать бесконечно.

### 10.7. Приложение работает в RDP, но перестаёт подписывать после отключения сеанса

Возможные причины:
- пользователь вышел из системы, и его профиль/хранилище сертификатов больше не доступны процессу;
- RDP-сеанс завершён, а не просто отключён;
- CSP или носитель требует интерактивного PIN-диалога;
- токен был перенаправлен в RDP-сеанс и стал недоступен после отключения;
- процесс был завершён политикой сервера или настройкой завершения сеансов.

Проверьте разницу между блокировкой, отключением RDP и выходом пользователя из системы. Проведите испытания во всех трёх режимах. Если подписание должно выполняться без активной пользовательской сессии, переходите к отдельной фоновой архитектуре, описанной в разделе 2.5.

### 10.8. Подпись создаётся, но внешняя система её не принимает

Возможные причины:

-   системе нужен другой формат CAdES;
-   ожидается DER/CMS, а передан текстовый Base64;
-   различаются параметры attached/detached;
-   требуется другой профиль подписи;
-   ожидается метка времени;
-   не выполняется требуемая проверка цепочки или статуса сертификата;
-   не совпадает кодировка или представление исходных данных.

Сверьте требования принимающей системы с фактическим результатом Bridge.
Не считайте успешное создание файла доказательством совместимости.

## 11. Безопасность и тестовые данные

До прохождения испытаний используйте только тестовые документы и
тестовые сертификаты.

Обязательные правила:

-   не хранить PIN-коды в исходном коде, JSON, `.env`, настройках
    Flutter или логах;
-   не экспортировать закрытые ключи;
-   не копировать контейнеры закрытых ключей между машинами без
    утверждённой процедуры;
-   не включать реальные медицинские документы в тестовые наборы;
-   ограничить доступ к файлам подписи и диагностическим журналам;
-   не публиковать в Git реальные сертификаты, контейнеры, PIN-коды,
    закрытые ключи и документы;
-   не считать сам факт наличия сертификата доказательством его
    доверенности;
-   проверять права на каталоги, куда приложение записывает исходные
    файлы и подписи.

Перед внедрением в медицинскую или иную регулируемую среду согласуйте
порядок обработки документов, журналирования, хранения результатов и
реагирования на ошибки с ответственными специалистами организации.

## 12. Ограничения текущей реализации

Текущий модуль является интеграционным каркасом. Следующие возможности
не следует считать реализованными или подтверждёнными без отдельной
разработки и испытаний:

-   импорт и установка сертификатов;
-   установка и перенос контейнеров закрытых ключей;
-   управление PIN-кодами и политиками носителей;
-   проверка attached-подписи отдельной командой;
-   полноценная проверка цепочки доверия;
-   полноценная проверка OCSP/CRL и статусов отзыва;
-   проверка меток времени;
-   поддержка всех профилей CAdES, требуемых внешними системами;
-   запись результатов подписания в базу Медиалог;
-   интеграция с Нетрикой;
-   проверка совместимости с конкретным контуром документооборота;
-   автоматическое развёртывание и обновление Bridge;
-   автоматизированный набор unit/integration-тестов на реальном
    оборудовании.

Особое внимание уделите формату подписи: текущая реализация получает
строковый результат `SignCades` и записывает его в UTF-8 файл. Перед
интеграцией с внешней системой нужно подтвердить, что именно такой
формат и расширение ожидаются принимающей стороной.

Также успешный `VerifyCades` в рамках текущей операции не следует
трактовать как полную юридически значимую проверку сертификата и доверия
к нему.

## 13. Дополнительные проверки для Windows Server

Перед вводом сервера в эксплуатацию проверьте:

1. Точную редакцию и версию Windows Server.
2. Запуск приложения после перезагрузки сервера.
3. Запуск под той учётной записью, которая будет использоваться в эксплуатации.
4. Наличие сертификата и закрытого ключа в контексте именно этой учётной записи.
5. Работу подписи при активной RDP-сессии.
6. Поведение при блокировке и отключении RDP-сеанса.
7. Поведение после выхода пользователя из системы.
8. Доступность токена/носителя после переподключения RDP.
9. Работу после планового обновления или перезагрузки сервера.
10. Права на каталоги приложения, временные файлы, исходные документы и результаты подписи.
11. Совместимость версий Windows Server, КриптоПро CSP, CAdESCOM и драйверов носителя.
12. Наличие резервного сценария на случай недоступности криптопровайдера или носителя.

Если сервер должен подписывать документы автоматически, без оператора и активного RDP-сеанса, текущую реализацию нельзя считать готовой к такому режиму. Сначала необходимо реализовать и отдельно испытать серверный worker/service.
